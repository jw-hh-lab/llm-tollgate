# 크레딧 동시성 검증 결과 (MySQL 8.4, 2026-11-22)

## 한 줄 결론

같은 고객의 요청이 최대 300개까지 동시에 몰려도 **잔액은 한 번도 음수가 되지 않았고, 잔액은 항상 원장 합계와 같았다.** 다만 같은 고객의 요청은 잔액 행 하나를 두고 줄을 서기 때문에, 같은 부하를 고객 20명에게 나눴을 때보다 처리량이 약 2.4~2.7배 낮았다.

## 어떻게 측정했나

- 테스트: `app/gateway/src/test/java/com/llmtollgate/gateway/credit/CreditConcurrencyMySqlTest.java`
- DB: Testcontainers로 띄운 **MySQL 8.4** (k8s 매니페스트와 같은 버전). 운영과 같은 Flyway 스키마
- 방식: 스레드를 요청 수만큼 만들어 모두 준비시킨 뒤 동시에 출발시킨다. 커넥션 풀은 HikariCP 기본값 10개
- 환경: Windows 노트북 + Docker Desktop. **시간 숫자는 환경과 실행마다 달라진다.** 정확성(성공 수, 잔액, 원장 일치)은 매번 같다
- 다시 실행: `cd app && ./gradlew :gateway:test --tests '*CreditConcurrencyMySqlTest'` → `gateway/build/reports/concurrency/mysql-credit.md`

## 결과 (전체 테스트 실행 기준)

| 시나리오 | 무엇을 확인하나 | 결과 | 요청 하나 처리 시간 p50 / p95 | 처리량 |
| --- | --- | --- | --- | --- |
| 1. 잔액 100에 80짜리 예약 100개 | 흐름도 문서의 예시 그대로 | 성공 1, 거절 99, 잔액 20 | 48 / 84 ms | 1,098 요청/초 |
| 2. 잔액 10,000에 100짜리 예약 200개 | 딱 맞는 잔액에서 정확히 끊기는가 | 성공 100, 거절 100, 잔액 0 | 546 / 618 ms | 317 요청/초 |
| 3. 예약 300 + 무작위 정산 300개 (잔액 50,000) | 예약과 정산이 섞여도 맞는가 | 성공 170, 거절 130, 잔액 23,951 = 50,000 − 실제 차감 26,049 | 1,043 / 1,678 ms | 172 요청/초 |
| 4. 실제 요청 흐름 100개 (예약 → 가짜 Gemini → 정산 → 호출 기록) | 앱 흐름 전체에서 원장 = 호출 기록인가 | 성공 100, 잔액 800 = 1,000 − 호출 기록 차감 합계 200 | 945 / 1,009 ms | 96 요청/초 |
| 5. 시나리오 2와 같은 200개를 고객 20명에게 나눔 | 줄서기가 고객별인가 | 성공 200, 20명 모두 잔액 0 | 113 / 215 ms | 865 요청/초 |

같은 날 먼저 돌린 단독 실행에서는 시나리오 2가 222 요청/초(p95 879 ms), 시나리오 5가 537 요청/초(p95 353 ms)였다. 두 실행 모든 시나리오에서 잔액은 음수가 되지 않았고 원장 합계와 일치했다.

## 해석

1. **정확성은 보장된다.** 예약은 `UPDATE ... SET balance = balance - ? WHERE customer_id = ? AND balance >= ?` 한 줄이다. InnoDB가 이 행을 잠그고 조건을 최신 값으로 다시 확인하기 때문에, 동시에 들어온 요청도 잔액을 넘겨 통과하지 못한다. 별도의 락 코드 없이 시나리오 1~5가 모두 맞았다.
2. **대가는 같은 고객 안의 줄서기다.** 같은 고객의 예약·정산은 모두 잔액 행 하나를 수정하므로 한 번에 하나씩 처리된다. 시나리오 2(고객 1명)와 5(고객 20명)는 요청 수와 금액이 같은데, 고객을 나누자 처리량이 2.4~2.7배가 됐다. 앱 흐름도 문서에 적어 둔 약점 "잔액 행 하나에 요청이 몰림"이 숫자로 확인된 것이다.
3. **시나리오 3의 거절 130개는 정상이다.** 예약은 정산될 때까지 돈을 잡아 두기 때문에, 순간적으로 예약 합계(300 × 300 = 90,000)가 잔액(50,000)을 넘으면 나머지는 402로 거절된다. "예약된 돈이 잠시 묶인다"는 예약 후 정산 방식의 알려진 비용이다.

## 다음에 할 것

- 고객 한 명의 처리량이 실제로 부족한지는 배포 서버에서 k6로 다시 잰다 (가짜 LLM 모드, 9~10주차).
- 부족하면 고려할 방법: 잔액을 여러 행으로 나누기, Redis에서 먼저 차감하고 MySQL에 나중에 반영하기. 두 방법 모두 원장 대조가 복잡해지므로 숫자가 필요하다고 말할 때만 한다.
- 멱등성(같은 `Idempotency-Key` 동시 10개 → 차감 1번)도 같은 테스트 방식으로 검증한다.
